# Operational reliability of real-time visual anomaly detection for predictive maintenance

Code, results and dashboard for the MSc thesis *Operational Reliability Challenges in
Real Time Predictive Maintenance Systems in Smart Manufacturing* (Gaurang Rajanikant
Patel, FOM University of Applied Sciences, Essen, 2027).

Five anomaly-detection approaches from three paradigms are trained under one protocol on
two categories of [MVTec AD 2](https://www.mvtec.com/company/research/datasets/mvtec-ad-2)
and evaluated twice: on **predictive accuracy** under nominal conditions, and on
**operational reliability** — robustness to image degradation and real lighting change,
stability of the decision threshold, latency against a 1 s budget, sustained 1 Hz
streaming, and the behaviour of a prediction service.

| Paradigm | Models |
|---|---|
| Supervised classifiers | ResNet-50, EfficientNet-B0, ViT-B/16-384 (timm, ImageNet-pretrained) |
| Reconstruction | Convolutional autoencoder (trained from scratch) |
| Memory-based | PatchCore (implemented directly; ResNet-50 layer 2+3 features, 1 % coreset) |

## Main findings (sheet metal, mean of 3 seeds)

| | PatchCore | Autoencoder | ResNet-50 | EfficientNet-B0 | ViT |
|---|---|---|---|---|---|
| F1, nominal lighting (5 images) | 0.92 | 0.75 | 1.00 | 0.81 | 1.00 |
| AUROC, shifted lighting (25 images) | 0.79 | 0.45 | 0.66 | 0.63 | 0.88 |
| False positive rate, shifted lighting | 0.87 | 0.40 | 0.93 | 0.53 | 0.73 |
| Degraded conditions in which it flags every image | 90 % | 20 % | 60 % | 5 % | 13 % |
| Latency p95 on a Tesla T4 (ms) | 154.5 | 146.6 | 165.7 | 157.4 | 200.7 |

- **Speed is not the bottleneck.** Every model met the 1,000 ms budget: medians 92–138 ms,
  0 missed deadlines in 20,000 timed images; 65–90 % of the time is preprocessing of the
  native image, not the network.
- **The fixed threshold is.** A threshold selected on nominal validation images (only 4–5
  of them) drives most models into rejecting or passing whole classes of images once
  image quality or lighting changes.
- **Nominal accuracy does not predict robustness.** ResNet-50 is perfect under nominal
  lighting but ranks shifted images worse than PatchCore, which never saw a defect.
- The `can` category is at chance for every model: at the shared 384 px resolution its
  median defect shrinks from 9 × 25 px to about 2 × 9 px.
- The prediction service (FastAPI, local server, CPU) failed none of 4,000+ requests; a
  cold start costs 1.7–4.6 s, almost all of it model loading.

The evaluation sets are small (the public test split, grouped by physical part); the
thesis reports every number with its dispersion and limits. All numbers come from the
files in [`results/`](results) and the original run logs in [`logs_colab/`](logs_colab).

## Try the dashboard

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r app/requirements.txt
.venv/bin/streamlit run app/streamlit_app.py
```

The trained sheet-metal models (seed 0) are published as assets of the
[`v1.0-models` release](../../releases/tag/v1.0-models). The app downloads a model the
first time it is selected; the release URL is read from `app/weights/weights_url.txt`.
Upload any sheet-metal inspection image. No dataset images are distributed here.

The prediction API:

```bash
.venv/bin/pip install -r requirements-api.txt
.venv/bin/uvicorn app.api:app --port 8000
curl -F file=@part.png -F model=patchcore http://127.0.0.1:8000/predict
```

## Reproduce the experiments

1. **Data.** Request MVTec AD 2 from MVTec (CC BY-NC-SA 4.0, non-commercial use) and
   extract only the two categories, without the private test splits:
   ```bash
   tar -xzf sheet_metal.tar.gz -C data/mvtec_ad_2 --exclude='*/test_private*'
   tar -xzf can.tar.gz -C data/mvtec_ad_2 --exclude='*/test_private*'
   ```
2. **Environment.** `python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt`
3. **Run.** `python scripts/run_queue.py --profile colab` runs everything in order
   (30 trainings, Exp 1–5, figures); finished steps are recorded in `logs/done.txt` and
   skipped on restart. On Google Colab, use [`notebooks/thesis_colab.ipynb`](notebooks).

| Step | Command | Writes |
|---|---|---|
| Data check, lighting labels | `python scripts/00_verify_data.py` | `lighting_*.csv` |
| Image cache, splits | `python scripts/01b_build_cache.py --category sheet_metal` then `01_make_splits.py` | `splits_*.csv` |
| Train | `python scripts/02_train.py --model patchcore --category sheet_metal --seed 0` | `artifacts/…`, `training_log.csv` |
| Exp 1 — nominal accuracy | `python scripts/03_eval_nominal.py --model patchcore --category sheet_metal` | `exp1_predictive.csv` |
| Exp 2+3 — degradation, lighting, threshold | `python scripts/04_eval_reliability.py …` | `exp2_reliability.csv` |
| Exp 4 — latency | `python scripts/05_bench_latency.py …` | `exp4_latency_*.csv` |
| Exp 5 — 1 Hz stream, window sweep | `python scripts/06_stream.py …` | `exp5_*.csv` |
| Exp 6 — service | `python scripts/07_load_test.py --base-url … --image …` | `exp6_service*.csv` |
| Figures and tables | `python scripts/08_make_figures.py` | `figures/`, `table5_*.csv` |

Any configuration value can be overridden with `--set key.sub=value`; `--device
cpu|mps|cuda` selects the device. Re-running a configuration replaces its rows.

## Deploying the dashboard (Streamlit Community Cloud)

1. Fork or use this repository; the model weights stay in the release.
2. On [share.streamlit.io](https://share.streamlit.io): *Create app* → this repository,
   branch `main`, main file `app/streamlit_app.py`, Python 3.12.
3. Streamlit installs `app/requirements.txt` (CPU-only PyTorch). One model is resident
   at a time; switching models reloads weights and the load time is shown.

## Design decisions

Choices made during implementation that the thesis relies on (numbered as in the
development log).

- **D0 Lighting from filenames.** Every test image is named `<part>_<condition>.png`
  with condition ∈ {regular, overexposed, underexposed, shift_1, shift_2, shift_3};
  training images are all `regular`. `regular` → nominal, the other five → shifted.
- **D1 Part-grouped split.** Each test part is photographed under all six conditions
  (can: 12 good + 15 defective parts; sheet_metal: 4 + 15). The 50:20:30 re-split is
  done over *parts*, stratified by label, so all six variants of a part land in the
  same portion (`split.group_by: part`). An image-level split would put the same
  defect in training and evaluation under different lighting. Resulting eval portion:
  can 4+4 nominal / 20+20 shifted images; sheet_metal 1+4 nominal / 5+20 shifted.
- **D2 Threshold calibration set.** The F1-maximising threshold is selected for all
  five models on the nominal-lighting part of the re-split `val` portion — the only
  nominal validation data containing anomalies (`official_val` is defect-free).
  Stored in `artifacts/…/calibration.json`, reused everywhere.
- **D3 CAE early stopping on validation reconstruction loss**, since `val_f1` is
  undefined on the defect-free `official_val`. CAE uses `cae.lr` 1e-3 and
  `cae.max_epochs` 100 from the plan's config; Chapter 3.5 says "same optimiser and
  schedule", which is true of optimiser and schedule shape but not of lr/epochs.
- **D4 PatchCore grid** is 24 × 24 (576 patches) as the plan's numbers state: layer2
  (48 × 48) is bilinearly resized onto layer3's 24 × 24 grid. The saved artefact
  includes the frozen backbone so loading needs no download; `size_mb` = backbone
  (fp32) + fp16 bank.
- **D5 Augmentation** is off for PatchCore's memory bank; on for the other four.
- **D6 AMP** only on CUDA; on MPS/CPU training runs in fp32.
- **D7 Timing input.** Latency and stream runs feed encoded native-resolution PNGs held
  in memory, so `t_pre` includes decode, validation and resize from full resolution.
  `input_source` in the summary records this.
- **D8 Stream queueing.** Arrivals are on a fixed 1 Hz schedule; a late result delays
  the next image, and that wait is included in `e2e_ms`.
- **D9 Window sweep parameters** (`realtime.step_change`): prevalence 0.1 → 0.6 at
  index 1000 of a 2000-image sequence, 50 trials, built from the model's real decisions
  on eval images. Indication = full window and rate > threshold (strict).
- **D10 ECE** is top-label ECE (15 equal-width bins); CAE/PatchCore scores are min–max
  normalised with calibration-set percentiles 1 and 99.
- **D11 Extra columns/files:** `filename`, `score` in `exp5_stream.csv`;
  `n_trials_detected`, `n_trials` in the sweep; timing decomposition, `input_source`,
  `peak_mem_kind` in the latency summary; `patchcore_construction.csv`;
  `table5_*.csv`. Extra dependencies: `psutil`, `python-multipart`; separate
  `requirements-api.txt`.
- **D13 Primary category is `sheet_metal`, not `can`.** At the common 384 × 384 input,
  most `can` defects shrink to a few pixels, below the scale the models resolve, and
  every model is near chance on it; `sheet_metal` defects survive the resize. `can` is
  kept as the secondary category, the case where the shared working resolution falls
  below the defect scale. The `sheet_metal` nominal evaluation set holds a single good
  part, so its nominal figures are indicative only.
- **D14 CAE image score stays the mean per-pixel L1.** The autoencoder localises
  defects at pixel level (defect pixels reconstruct with 2.6–3.4× the error of normal
  pixels), but the image mean dilutes small defects; alternatives such as the peak of
  the smoothed map did no better in development, because the largest errors sit on the
  plate borders of good and defective images alike.
- **D16 Where things ran.** All 30 trainings and Exp 1–5 run on one Google
  Colab instance (NVIDIA T4) via `notebooks/thesis_colab.ipynb` (`run_queue.py --profile colab`:
  AMP fp16, ResNet-50/EfficientNet-B0/CAE at batch 16, ViT 8 × 2, two data-loading
  workers). Earlier Apple M2 runs were development only and are discarded by the
  notebook. All timing runs on one GPU type: if a reconnect assigns a different GPU,
  every timing step is re-run (`logs_colab/timing_gpu.txt`). Figures and tables are drawn
  from the results files; Exp 6 ran on a local server (Apple M2, CPU inference).
- **D17 Shorter stream (Exp 5).** 500 images at 1 Hz × 2 repeats per model (plan:
  2000 × 3), and on the primary category sheet_metal only (`--stream-categories`), to
  keep the full Colab run to ~4 h. Still 5× the longest sliding window (100) and still
  repeated for the consistency check; Section 5.5 reports stability "over 500
  consecutive images" for sheet_metal. Exp 4 (latency) still covers both categories.
  The window sweep (synthetic 2000-image step change) is unaffected.
- **D12 Hosting.** Streamlit Community Cloud serves only the Streamlit app; the FastAPI
  service needs its own host. Weights are release assets (the ViT is 328 MB, above
  GitHub's 100 MB file limit) downloaded on first use (`src/serving.py`).
